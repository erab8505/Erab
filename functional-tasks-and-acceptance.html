1. How to Use This Document

Each task is a runnable user story. Execute its workflow as the stated role and mark each acceptance item only after it is observed in the user interface or verified from the API. “Current behavior” describes the functionality as implemented, even where it should be tightened for a production clinical system.

Test data dependency: create a company, area, specialty, active specialist with availability, and intervention before testing scheduling. Create a patient and appointment before testing records and prescriptions.

3. Foundation Tasks

F-01

Authenticate and establish a session

Actors: AdminReceptionistSpecialist | Client route: /login | API: POST /auth/login

End-to-end workflow

  1. User opens the login screen and submits username and password.
  2. The client sends credentials to the API; the API verifies the BCrypt password hash and returns authenticated user data, allowed companies, role, and JWT.
  3. The client stores the JWT in session storage and keeps the authenticated user in application state.
  4. Admin is sent to /admin/select-company. A non-admin with one company is assigned it automatically; otherwise they select a company.
  5. Every subsequent request includes Authorization: Bearer <token>.

Acceptance criteria

  • Valid credentials create a session and route according to role/company count.
  • Invalid credentials show an error and do not create a session.
  • Protected routes redirect an unauthenticated visitor to login.
  • Expired or invalid JWT responses result in a usable signed-out state.
  • No plain password is persisted, displayed, or logged.
F-02

Select and switch active company

Actors: all authenticated users | Routes: /select-company, /admin/select-company | Header: X-Company-Id

End-to-end workflow

  1. User opens the company selector after login or through Switch Company.
  2. Non-admin selects from assigned companies; Admin selects a company from the company management view.
  3. Client saves the active company context and attaches its ID to API requests.
  4. API middleware resolves the active company from the header or token claim.
  5. Client routes to dashboard and reloads tenant-scoped content.

Acceptance criteria

  • A company context is required before entering dashboard and functional routes.
  • A user can only select companies assigned to them; Admin behavior follows the configured administrative policy.
  • Changing company clears or reloads lists, forms, and dashboards so prior tenant data is not shown.
  • An invalid or unauthorized company ID is rejected by the API.
  • Requests for tenant data include the active-company header.
F-03

Use the application shell

Actors: all authenticated users | Shared layout: navbar, role-aware sidebar, theme control, notifications

End-to-end workflow

  1. After company selection, user enters the shared layout.
  2. Navbar shows active company and role; sidebar presents permitted modules only.
  3. User navigates between lazy-loaded pages, changes theme, receives success/error/warning toast messages, or logs out.
  4. Logout clears authentication and company state, then returns to login.

Acceptance criteria

  • Navbar identifies the selected company and current role.
  • Sidebar does not render administration items for Receptionist or Specialist.
  • Theme choice persists through navigation and reload.
  • Toasts are readable, dismissible, and auto-dismiss after the configured period.
  • Logout prevents access to protected routes until next successful login.
F-04

View role-appropriate dashboard

Actors: all authenticated users | Route: /dashboard

End-to-end workflow

  1. User enters dashboard with an active company.
  2. Admin client loads company areas, specialties, specialists, and interventions in parallel to render a collapsible organization tree.
  3. Receptionist/Specialist client loads patients and derives total, male, and female counts plus a quick-view list.
  4. User opens patient profile or uses permitted edit/delete actions from the tree.

Acceptance criteria

  • Dashboard content changes by role and active company.
  • Admin tree represents Company → Area → Specialty → Specialists/Interventions.
  • Tree edit actions route to matching edit screen; deletion respects dependency restrictions.
  • Patient dashboard reports counts from the active company only.
  • Patient quick-view opens the selected patient profile.

4. Administration Tasks

A-01

Manage companies

Actor: Admin | Routes: /companies, /companies/new, /companies/:id/edit | API: /companies

End-to-end workflow

  1. Admin lists companies or searches/filter them in company selection.
  2. Admin opens new or edit form and supplies name, tax ID, contact details, active state, and description.
  3. Client validates fields, calls create/update API, and displays the saved result.
  4. Admin can select the company to establish context or delete it when no restrictions block removal.

Acceptance criteria

  • Only Admin can create, update, or delete companies.
  • Required fields and email format are validated before submission and by API.
  • Created/edited values appear in the list and selection view without stale data.
  • Inactive state is visually clear and honored by relevant selection policy.
  • Delete failure due to dependent data produces an actionable error without partial deletion.
A-02

Manage areas and specialties

Actor: Admin | Routes: /areas, /specialties | APIs: /areas, /specialties

End-to-end workflow

  1. Admin selects company and opens Areas to create/edit/delete an organizational area.
  2. Admin opens Specialties and selects an existing area from the active company.
  3. Client saves name/description and parent association; API persists the entity under active company.
  4. Updated hierarchy becomes available to specialist, intervention, dashboard, and booking screens.

Acceptance criteria

  • Lists display only selected-company areas/specialties.
  • Area is mandatory when creating or editing a specialty.
  • Specialty selection cannot reference an area from another company.
  • Required names are enforced; edits update all dependent selection labels.
  • Deleting a parent with child data is refused with a clear message.
A-03

Manage specialists and weekly availability

Actor: Admin | Routes: /specialists, /specialists/:id/availability | APIs: /specialists, /specialist-availability

End-to-end workflow

  1. Admin creates a specialist with identity, license, contacts, specialty, and active state.
  2. Admin opens availability, chooses a weekday and from/to time, then adds recurring time intervals.
  3. API saves availability linked to specialist; client displays each interval as a day chip.
  4. Admin removes an interval when it is no longer valid. Booking later retrieves availability and booked appointments to calculate slots.

Acceptance criteria

  • Specialist must have first name, last name, license number, specialty, and email as required by form.
  • Specialty choices are limited to active-company specialties.
  • Availability has weekday, valid local start/end times, and a specialist association.
  • Added interval is visible immediately and survives reload; removed interval no longer appears.
  • Inactive specialists are not offered for new bookings.
A-04

Manage intervention types

Actor: Admin | Routes: /interventions | API: /intervention-types

End-to-end workflow

  1. Admin opens intervention list for active company.
  2. Admin creates or edits a procedure with name, specialty, description, duration, optional code, flags, and active state.
  3. API validates and persists the catalogue item under company and specialty.
  4. Booking wizard filters active interventions by selected specialty; clinical notes can link an intervention.

Acceptance criteria

  • Name, specialty, description, and duration are required.
  • Duration is a positive number of minutes.
  • Specialty is tenant-scoped and cannot be cross-company.
  • Anesthesia, hospitalization, and active flags save and display correctly.
  • Inactive interventions are unavailable for new appointment selection.
A-05

Manage user accounts and company membership

Actor: Admin | Route: /users | API: /users

End-to-end workflow

  1. Admin lists users and opens a create or edit form.
  2. Admin sets username, password for a new account, role, linked specialist where applicable, and one or more company assignments.
  3. API stores the BCrypt hash, role, specialist link, and UserCompany memberships.
  4. On next login the user receives their role and company claim set and follows the relevant company selection flow.

Acceptance criteria

  • Only Admin can access user list and mutation APIs.
  • Username is unique and duplicate submission returns a useful error.
  • User has a valid role and at least the required company assignments.
  • Edited memberships affect company choices at next authenticated session.
  • Deleting a user removes their membership access and prevents future login.

5. Patient and Clinical Tasks

C-01

Register, search, update, and remove patients

Actors: AdminReceptionistSpecialist | Routes: /patients, /patients/new, /patients/:id/edit | API: /patients

End-to-end workflow

  1. User opens patient list scoped to active company and searches by patient details.
  2. User creates or edits demographics, contact data, document ID, birth date, gender, blood type, and allergies.
  3. API persists the patient under active company and returns refreshed details.
  4. User opens profile, starts booking with patient preselected, or Admin deletes the patient when allowed.

Acceptance criteria

  • Patient list/search returns only active-company patients.
  • First/last name, document ID, birth date, and gender are required.
  • Age is computed from birth date and displays correctly.
  • Blood type, allergy, contact values persist and display in profile.
  • Only Admin sees/executes deletion; dependent data prevents unsafe deletion or follows documented retention policy.
C-02

Review a patient profile and clinical timeline

Actors: AdminReceptionistSpecialist | Route: /patients/:id

End-to-end workflow

  1. User selects View on a patient list/dashboard row.
  2. Profile loads demographics, patient appointments, medical records, and prescriptions.
  3. User switches among Personal Info, Appointments, Medical Notes, and Prescriptions tabs.
  4. Permitted users open clinical forms, print prescriptions, or return to booking/edit flows.

Acceptance criteria

  • All tabs refer to the same selected patient and active company.
  • Personal data displays computed age, blood type, and allergies.
  • Appointment rows show date/time, specialist, intervention, and status.
  • Clinical notes and prescriptions refresh after creation/deletion.
  • Unknown or out-of-tenant patient ID does not expose data.
C-03

Create and maintain medical records

Current API actor: any authenticated user; required policy: Admin or assigned Specialist | API: /medical-records

End-to-end workflow

  1. User opens a patient profile Medical Notes tab and starts a new note.
  2. User supplies record date, optional intervention, required diagnosis, optional treatment/notes, and available vital signs.
  3. Client posts to API; API links record to patient and company; the profile reloads the notes list.
  4. Permitted user updates or deletes the record when business policy allows.

Acceptance criteria

  • Diagnosis is mandatory and supports the configured length.
  • Patient and optional intervention belong to active company.
  • Vitals preserve decimal/integer values without locale corruption.
  • New/updated note appears in chronological patient history.
  • Current build allows any signed-in role; production acceptance requires server rejection for Receptionist and unassigned Specialist.
C-04

Issue, view, delete, and print prescriptions

Current API actor: any authenticated user; required policy: Admin or assigned Specialist | Print route: /patients/:id/prescriptions/:rxId/print | API: /prescriptions

End-to-end workflow

  1. User starts a prescription from patient Medical Notes or Prescriptions.
  2. User selects prescribing specialist, optional medical record, date/notes, and one or more medication lines with dosage, frequency, duration, and instructions.
  3. API saves header and items; patient profile reloads prescription list.
  4. User opens Print to render company/patient/specialist information and medication table in print-ready view; permitted user may delete.

Acceptance criteria

  • Prescription is linked to active-company patient and specialist; optional record belongs to same patient/company.
  • Each item has medication, dosage, frequency, and valid positive duration.
  • Prescription list identifies specialist, date, and medication summary.
  • Print view contains company letterhead, patient demographics, specialist/specialty, prescription date, lines, and notes.
  • Current build permits any signed-in role; production acceptance requires clinical role/ownership enforcement and auditable issuance.

6. Scheduling Tasks

S-01

Book an appointment using the guided wizard

Actors: AdminReceptionistSpecialist | Route: /scheduling/new | API: POST /scheduling

End-to-end workflow

  1. User starts from Scheduling or chooses Schedule on a patient, which preselects the patient.
  2. Wizard selects Patient → Area → Specialty → Intervention → Specialist → Date and time.
  3. Each selection filters downstream choices. Date selection requests specialist availability/appointments and presents 30-minute slots.
  4. User selects an available slot and confirms. API validates specialist/company relationship, availability, and overlap, then creates a Scheduled appointment.
  5. Success toast appears and scheduling/patient profile lists show the new booking.

Acceptance criteria

  • Only active-company patient, area, specialty, intervention, and specialist options can be selected.
  • Changing an upstream selection clears invalid downstream selections.
  • Past dates and unavailable/booked slots cannot be confirmed.
  • Slot calculation honors specialist weekly availability and intervention duration.
  • API rejects mismatched company references and conflicting specialist intervals, including concurrent submissions.
S-02

View and filter appointments

Actors: AdminReceptionistSpecialist | Route: /scheduling | APIs: GET /scheduling, patient/specialist filtered GETs

End-to-end workflow

  1. User opens Scheduling list for selected company.
  2. Client retrieves appointments and shows patient, specialist, intervention, date/time, and status.
  3. Patient profile requests appointments for its patient; slot generation requests a specialist’s appointments for a date.
  4. User proceeds to permitted status actions or booking flow.

Acceptance criteria

  • List displays correct joined names and active-company appointments.
  • Patient-specific list contains only that patient's appointments.
  • Specialist/date query returns relevant date appointments for slot exclusion.
  • Status visual treatment distinguishes Scheduled, Confirmed, Completed, Cancelled, and Rescheduled where returned.
  • Out-of-tenant IDs are rejected or return not found without data leakage.
S-03

Update appointment status and reschedule

Actors: current API: authenticated users; required policy: Admin, Receptionist, or assigned Specialist | APIs: PATCH /scheduling/{id}/status, PATCH /scheduling/{id}/reschedule

End-to-end workflow

  1. User opens an appointment in the list and selects Mark Done, Cancel, Confirm, or Reschedule when offered.
  2. For status, client sends target enum status; for reschedule, client chooses a newly valid date/time and submits it.
  3. API updates status or checks new availability/conflicts before changing time and marking the appointment Rescheduled.
  4. Client replaces/refetches the appointment and slot availability reflects the change.

Acceptance criteria

  • Only valid transitions are offered and accepted; completed/cancelled appointments cannot be casually edited.
  • Status result is immediately visible in scheduling and patient profile.
  • Rescheduling rejects unavailable/past/conflicting times and leaves original booking intact on failure.
  • Rescheduling releases old slot and blocks new slot after success.
  • Specialist may change only appointments they are authorized to manage; all roles are checked server-side.
S-04

Delete an appointment

Actor: Admin | API: DELETE /scheduling/{id}

End-to-end workflow

  1. Admin selects delete from a permitted appointment list action and confirms intent.
  2. Client sends delete request for selected appointment.
  3. API removes the appointment or returns not found/error.
  4. Client removes/refetches the row and affected specialist slot becomes available for future bookings.

Acceptance criteria

  • Only Admin receives a successful delete response.
  • Deleting unknown or out-of-tenant appointment does not reveal information.
  • Successful deletion removes it from all appointment lists and slot calculations.
  • Failure leaves the user interface and persisted appointment consistent.
  • Production policy records who deleted it and why, or uses cancellation instead for clinical auditability.

7. Cross-Cutting Acceptance

AreaAcceptance criteria for every applicable task
AuthorizationUnauthenticated requests receive 401; unauthorized roles receive 403. Server enforcement matches the intended role table, independent of route guards or hidden buttons.
Tenant isolationEvery list, item lookup, mutation, and referenced foreign key is constrained to the resolved active company. Manipulating an ID or X-Company-Id never exposes another tenant.
Validation and failuresRequired fields, formats, ranges, duplicate constraints, and incompatible entity relationships return actionable errors. Client preserves submitted data when a request fails where safe.
Data consistencyCreates/updates/deletes refresh affected lists, dashboard counts, patient profiles, and scheduling slot results. No screen shows stale data after a successful action.
Accessibility and responsive behaviorForms have labels and keyboard operation, error messages are announced/visible, focus is managed after navigation/modal changes, and tables/forms remain usable on narrow screens.
Observability and safetyHealth endpoints report service/database health; logs have request context without passwords, JWTs, or clinical text. Production uses HTTPS, secret storage, origin-specific CORS, backups, and audit retention.
Completion definition: a task is complete only after its happy path, validation failure, authorization failure, tenant-isolation attempt, and data-refresh behavior all pass in the UI and corresponding API test coverage.
