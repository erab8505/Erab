1. Product Scope

MedApp manages one or more medical companies. A company contains areas, specialties, professionals, intervention definitions, patients, appointments, clinical records, and prescriptions. Users operate in one active company at a time; their role determines which workflows they can perform.

Administration

Manage companies, company membership, areas, specialties, professionals, availability, and intervention catalogues.

Reception

Register and find patients, inspect schedules, create, confirm, cancel, and reschedule appointments.

Clinical Care

Review assigned appointments and patient histories, document visits, record vital signs, and issue prescriptions.

Roles

RoleCompany accessPermitted workflows
AdminAny company selected in the application; current API treats Admin as unrestricted.All administration, patient, appointment, record, and prescription operations.
ReceptionistOnly assigned companies.Patients and scheduling. No catalogue, membership, clinical record, or prescription mutation.
SpecialistOnly assigned companies and a linked specialist profile.Own availability and appointments; patient history for care; create records and prescriptions for appointments they own.

2. Review Findings

The .NET solution and Angular client both build successfully. These are the issues to address while recreating or hardening the application.

High: clinical write endpoints are too broadly authorized. The API marks all medical-record and prescription endpoints as authenticated, so a receptionist can create, alter, or delete clinical data. Require Admin/Specialist, then verify that the specialist is linked to the request user and owns the related appointment or patient-care context.
High: tenant authorization must be server-side for every resource. The active company is derived from a header or token, but services accept entity IDs and some DTOs carry CompanyId. Every read, update, and delete must query by both entity ID and the resolved company. Validate every foreign key belongs to that same company before persistence. Do not trust a request body company ID.
Medium: migrations are bypassed. API startup calls EnsureCreatedAsync() although EF migrations and an ApplyMigration project exist. Use Database.MigrateAsync() for a migrated database, preferably from a deployment job, and never mix the two initialization approaches.
Medium: dependency security warning. The backend build reports a known high-severity advisory for AutoMapper 13.0.1 (GHSA-rvv3-g6hj-g44x). Upgrade to a fixed supported release after checking API compatibility and lock the resolved version.
Client build quality. Angular reports invalid nested CSS around toast custom properties, an unused dashboard import, two needless optional chains, and five component stylesheets over the 4 kB budget. Correct the CSS syntax, remove/simplify the TypeScript/template code, and either reduce styles or intentionally adjust budgets.
Deployment concern. AllowAnyOrigin().AllowAnyMethod().AllowAnyHeader() and a development localhost API URL are appropriate only for local development. Allow only deployed UI origins and inject environment-specific API URLs for staging and production.

4. Database Schema

Use UUID/GUID primary keys. Every entity except the membership join has Id, CreatedAt (UTC), and nullable UpdatedAt. Store instants in UTC; define the clinic time zone explicitly when producing appointment slots.

Appointment integrity: the current index on (SpecialistId, ScheduledAt) is not unique and cannot prevent overlapping variable-duration interventions. Before insert/reschedule, load appointments for the specialist in the requested interval and reject any intersection: existing.Start < requested.End AND requested.Start < existing.End.

5. Security and Tenancy

  1. Create a BCrypt password hash; never persist or log a plain password.
  2. On login, verify the user and produce a short-lived signed JWT containing subject/user ID, username, role, and allowed company IDs.
  3. Client stores the token in session storage, attaches Authorization: Bearer <token>, and attaches the selected X-Company-Id.
  4. Middleware validates the requested company against membership claims, resolves request-scoped ICompanyContext, and returns 403 for unassigned companies.
  5. Services derive company from context, filter all queries by it, and validate referenced IDs belong to it. Controllers must not bind CompanyId from request DTOs.
  6. Authorize writes by policy and ownership. Log actor, company, action, entity, and correlation ID without medical data or tokens.

Use HTTPS, secret storage for the JWT signing key and connection string, token-expiry handling, login rate limits, and production CORS allowlists. Medical data also calls for audit trails, backups, retention policy, least privilege, and jurisdiction-specific privacy controls.

8. Client Application

Use lazy-loaded feature routes protected by authGuard, companyGuard, and a parameterized roleGuard. The shell contains responsive navigation, current-company switcher, theme control, and global toast/error handling.

Core

Configuration, auth, company context, interceptor, models, API services, guards, theme service, shared form/table/toast components.

Administrative features

Companies, areas, specialties, specialists with weekly availability, users, and intervention types. Each feature has list and create/edit form views.

Operational features

Patient list and profile; scheduling list/form/calendar behavior; specialist and patient dashboards; record and prescription views including print layout.

Client safeguards

  • Hide unsupported controls by role, but rely on API authorization as the decisive check.
  • Reload or invalidate tenant data whenever the active company changes.
  • Use server validation errors at field level, disable submit during requests, and preserve unsaved form data only deliberately.
  • Keep the access token out of local storage; session storage reduces persistence but does not mitigate XSS, so apply CSP and strict input/output handling.

9. Rebuild Steps

  1. Install a supported .NET SDK matching the solution target framework, Node.js LTS, npm, Angular CLI 19, and SQLite. Create private configuration for JWT and connection secrets.
  2. Create Domain, Application, Infrastructure, Api, and optional ApplyMigration projects. Api references Application/Infrastructure; Infrastructure references Application/Domain; Application references Domain.
  3. Define entities, enums, DTOs, repository contracts, and use-case services. Add request validation. Do not expose EF entities directly.
  4. Configure EF Core mappings using this schema, indexes, uniqueness and tenant predicates. Generate an initial migration with dotnet ef migrations add InitialCreate --startup-project ../MedApp.Api.
  5. Configure password hashing, JWT claims, company context, exception mapping, logging, health checks, Swagger bearer security, rate limiting, CORS, and authorization policies.
  6. Implement in dependency order: company/membership, catalogue, professionals/availability, patients, scheduling/slots, records, prescriptions. Cover races with a transaction and concurrency strategy.
  7. Implement controllers and integration tests for auth, roles, cross-tenant IDs, foreign keys, schedule conflicts, and lifecycle behavior.
  8. Create Angular standalone app. Implement core services/interceptor/guards, shell/company selection, then feature modules in the same dependency order.
  9. Build typed reactive forms, accessible validation, empty/loading/error states, tables/search/filtering, appointment status controls, timeline, and print stylesheet. Use environments for URLs.
  10. Seed non-production data only. Deploy migrations separately; configure HTTPS, CORS, secrets, backups and monitoring; run automated and role-based acceptance tests.

10. Acceptance Checklist

  • Admin can create hierarchy and assign users; non-admin API calls are rejected.
  • A user cannot select, read, alter, or infer records from an unassigned company.
  • Patient documents and specialist licenses are unique per company; parent/child company mismatches are rejected.
  • Slots respect availability and duration; concurrent booking cannot create an overlap.
  • Only Admin or properly linked Specialist writes records/prescriptions; every clinical action is audited.
  • Expired tokens require sign-in; production accepts only trusted CORS origins and HTTPS.
  • API tests and Angular production build pass without security, compiler, CSS, or budget warnings.
  • Accessibility covers keyboard operation, labels, focus, feedback, contrast, responsive tables, and printable prescriptions.
